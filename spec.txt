TPT App AV Commissioning

1. Product Definition

Product name: TPT AV Commissioning
Repository: tpt-app-av-commissioning
Product family: TPT Apps
Category: Professional audiovisual system commissioning, validation, diagnostics, and handover
Primary distribution: Offline desktop application
Primary target: AV integrators, commissioning engineers, systems engineers, and facilities teams
Target platforms: Windows first; Linux/macOS when device and driver support justify them

1.1 Executive summary

TPT AV Commissioning is a professional desktop application for commissioning, testing, diagnosing, documenting, and handing over audiovisual installations.

The application turns a collection of AV devices and connections into a structured, testable system.

Instead of an engineer manually checking every display, projector, audio path, control endpoint, network-controlled device, and signal route, the application provides:

A project/system inventory.

A device and endpoint model.

A connection and signal-path model.

Reusable commissioning test suites.

Automated and semi-automated tests.

Interactive diagnostics.

Evidence capture.

Defect tracking.

Repeatable regression testing.

Professional commissioning and handover reports.

The product should be designed around a simple proposition:

Commission an AV system once, prove that it works, and retain a repeatable record that it still works later.

This is intentionally narrower than a general AV control platform. The product's job is to test and prove the installation, not operate the venue during normal use.

2. Commercial Objective

The target customer is a professional AV integrator whose profitability depends on getting installations commissioned and handed over quickly.

3. Problem Being Solved

AV installations are often assembled from devices that each work individually but can fail when combined.

Examples:

Source
  ↓
Network / HDMI / SDI
  ↓
Switcher
  ↓
Scaler
  ↓
Display

or:

Microphone
  ↓
DSP
  ↓
Amplifier
  ↓
Speaker

or:

Control panel
  ↓
Control processor
  ↓
Projector
  ↓
Feedback

Commissioning must therefore test systems and signal paths, not merely individual devices.

Typical problems include:

incorrect routing

missing signal

EDID problems

resolution mismatch

HDCP problems

audio routing errors

incorrect channel mapping

excessive latency

audio/video sync problems

device-control failures

network connectivity failures

wrong configuration

intermittent failures

incorrect labels

incomplete documentation

The application should model these relationships explicitly.

4. Product Principles

4.1 Offline first

Core functionality must work without internet access.

No cloud account is required.

Internet may optionally be used for:

software updates

licence activation

optional device-driver updates

optional documentation updates

The application must remain usable in secure facilities with no internet access.

4.2 Test the system, not only the device

A device test answers:

Does the projector respond?

A system test answers:

Can source 3 be routed through switcher 2 to projector 1 at the required resolution, with the correct audio path and control feedback?

The second is the primary product value.

4.3 Evidence first

Every important test should be able to capture evidence.

Examples:

screenshot

measured signal

EDID

device response

audio measurement

latency measurement

network result

operator note

timestamp

4.4 Repeatability

A commissioning project should be executable again after:

firmware changes

equipment replacement

room modifications

maintenance

support incidents

This turns a one-time commissioning tool into a lifecycle validation tool.

4.5 Human-in-the-loop

Not every AV test can be automated.

Tests must support:

AUTOMATED
SEMI-AUTOMATED
MANUAL

Manual tests must be first-class citizens rather than awkward exceptions.

Example:

"Confirm image is visually free of artefacts."

The application presents the required test and asks the engineer to record:

Pass

9. Signal Path Model

The application must be able to represent a path:

Source A
   ↓
Matrix 1 input 3
   ↓
Matrix 1 output 7
   ↓
Scaler 2
   ↓
Projector 1

The path is a graph rather than a simple list.

struct SignalGraph {
    nodes: Vec<NodeId>,
    edges: Vec<EdgeId>,
}

This enables path-level testing.

A path can have requirements:

path:
  source: presentation-pc
  destination: projector-1

requirements:
  video:
    resolution: 3840x2160
    frame_rate: 60
    hdr: false

  audio:
    channels: 2

  latency:
    max_ms: 100

10. Device Driver Architecture

Device-specific communication must not leak into test logic.

trait DeviceDriver {
    fn identity(&self) -> DeviceIdentity;
    fn discover(&self) -> Result<DeviceState>;
    fn get_state(&self) -> Result<DeviceState>;
    fn execute(&self, command: DeviceCommand) -> Result<DeviceResponse>;
    fn capabilities(&self) -> DeviceCapabilities;
}

A driver may communicate using:

TCP

UDP

HTTP

WebSocket

OSC

MIDI

serial

vendor SDK

HID

Drivers should be asynchronous where protocol behaviour requires it.

10.1 Driver capabilities

Drivers should declare capabilities:

struct DeviceCapabilities {
    can_power_on: bool,
    can_power_off: bool,
    can_read_state: bool,
    can_select_input: bool,
    can_generate_test_pattern: bool,
    can_read_signal_status: bool,
    can_read_edid: bool,
    can_measure_latency: bool,
}

This prevents the test runner from assuming functionality that the device cannot provide.

        ↓
Device Discovery

15. Automated vs Manual Tests

Each test declares its execution mode.

enum ExecutionMode {
    Automated,
    SemiAutomated,
    Manual,
}

Automated

The software can determine the result.

SemiAutomated

The software prepares the test and captures measurements, but an engineer confirms the result.

Manual

The engineer performs the physical/visual test.

Example:

TEST: Projector Image Quality

1. Display test pattern.
2. Ask engineer to inspect:
   - focus
   - geometry
   - uniformity
   - dead pixels
   - visible artefacts
3. Capture screenshot.
4. Record result.

This is essential for real commissioning.

16. Test Procedure DSL

A declarative test format should be supported.

Example:

test:
  id: projector.signal-path
  name: "Projector Signal Path"

  steps:
    - command:
        device: matrix-01
        action: select_output
        args:
          output: 4

    - command:
        device: projector-01
        action: select_input
        args:
          input: hdmi1

    - wait:
        milliseconds: 1500

    - measure:
        type: video_signal
        device: projector-01

    - assert:
        field: resolution
        equals: "3840x2160"

    - assert:
        field: frame_rate
        equals: 60

The DSL should be validated before execution.

Do not allow arbitrary executable code in project files.

17. Test Runner

The runner must support:

dependencies

parallel execution

serial execution

timeouts

retries

cancellation

device locking

rate limits

evidence capture

result persistence

Example scheduling:

Room 1 network tests ────────┐
Room 2 network tests ────────┤
Room 3 network tests ────────┤
                             ↓
                       device tests
                             ↓
                     signal-path tests
                             ↓

Two tests must not simultaneously manipulate the same device unless the driver explicitly declares that it is safe.

18. Device Locking

A device should have an execution lock.

Example:

struct DeviceLock {
    device_id: DeviceId,
    owner: TestExecutionId,
}

This prevents:

Test A:
    Set matrix output 4

Test B:
    Set matrix output 8

from racing.

Signal-path tests should therefore declare the devices they mutate.

19. Measurement Model

Measurements must contain:

struct Measurement {
    name: String,
    value: MeasurementValue,
    unit: Unit,
    tolerance: Option<Tolerance>,
    source: MeasurementSource,
}

Examples:

Video Resolution = 3840x2160
Frame Rate = 59.94 fps
Audio Level = -20.3 dBFS
Latency = 83 ms
Packet Loss = 0.01 %

Measurements must preserve raw values where possible.

Do not round internally before evaluating tolerances.

36. Network Safety

This application will interact with real equipment.

Safety requirements:

explicit network interface selection

explicit target selection

configurable timeouts

configurable scan ranges

no unrestricted network scan by default

no destructive commands by default

confirmation before reboot/power-cycle tests

device locking

command logging

dry-run mode

A project should declare whether tests are permitted to change device state.

Example:

execution_policy:
  allow_power_cycle: false
  allow_configuration_changes: true
  allow_network_changes: false

37. Restore-State Mechanism

Tests that modify state must declare whether state restoration is supported.

Example:

Before:
Projector input = HDMI2
Brightness = 50

Test:
Set input = HDMI1

After:
Restore HDMI2
Brightness = 50

If restoration fails, the result must explicitly report:

Test passed, but device state restoration failed.

This is critical for safe professional use.

38. Security

The application may control physical equipment.

Requirements:

no arbitrary command execution from project files

no arbitrary shell commands in the test DSL

strict protocol parsing

bounded network reads

authentication support for device protocols

encrypted credentials where credentials are stored

OS credential store where practical

sensitive values excluded from reports by default

project access permissions handled by the OS

safe parsing of imported configuration files

Credentials must never be committed into project manifests.

54. Definition of Done

The first commercial release is ready when:

A complete AV project can be modelled.

Rooms can contain devices and endpoints.

Connections can form a signal graph.

Devices can have protocol drivers.

Generic network/control protocols work.

Tests can execute against devices.

Tests support dependencies and timeouts.

Device mutations are serialised safely.

Automated and manual tests are supported.

Evidence can be attached to results.

Failed tests can create defects.

Baselines can be created.

Current state can be compared against a baseline.

A commissioning report can be generated.

The report distinguishes automated and manual tests.

Project data works fully offline.

CLI and GUI use the same test engine.

Mock devices can simulate failures.

No malformed device response can crash the application.

Network scanning requires explicit configuration.

Destructive operations require explicit permission.

Tests that modify state can restore state or clearly report failure to restore.

A real AV installation has been commissioned with the software.

56. Strategic Boundary

tpt-app-av-commissioning must not become tpt-app-av-control.

Normal operation belongs to tpt-av-control and eventually the AV Automation product.

Control owns:

Operate
Route

The two products may share the same foundation and can eventually integrate, but their commercial purposes should remain distinct.

The most important product-level idea is therefore:

The AV system model is not merely documentation. It is an executable specification that can be tested against the physical installation.
